# Pod audit — 2026-08-24

## Scope

Public repository audit of `technodotventures/pod` focused on:
- whether Pod can coexist behind another memory system instead of replacing it;
- Smartware integration and MCP surfaces;
- packaging / CI consistency;
- security-sensitive auth and watch paths.

## Verification performed

- cloned the public Pod repo locally
- read `README.md`, `CONTEXT.md`, `AGENTS.md`, `docs/smartware-authority.md`, and the routing/auth code
- ran `npm install`
- ran `npm test` → 282 passing tests
- ran `npm run typecheck` → clean
- ran `npm audit --omit=dev` → 0 vulnerabilities
- booted the runtime and exercised `GET /health`, `GET /pod/capabilities`, `POST /pod/observe`, and `POST /pod/query`

## Summary answer

Pod can sit behind another memory system.

The clean shape is:
- Honcho remains the primary agent-memory product where the user wants it to be primary
- Pod becomes the evidence/provenance substrate behind it
- Hermes can query both, but Pod should own the durable receipts, citations, bitemporal history, and cross-app memory joins

The hard part is not technical reachability. The hard part is identity mapping and authority boundaries:
- which actor/peer ID in Honcho corresponds to which Pod actor?
- which facts are canonical in which system?
- how do mirrored conclusions avoid becoming duplicated truth?

## Findings

| ID | Severity | Status | Finding |
|---|---|---|---|
| POD-AUDIT-001 | High | fixed | Packaging / CI drift: the repo no longer contains `vendor/smartware`, and the release flow now restores the reviewed Smartware npm packages from `package-lock.json`. |
| POD-AUDIT-002 | Medium | fixed | Agent bearer tokens are stored plaintext in SQLite, unlike client tokens which are hashed. Fixed: `agents.auth_token` now stores `sha256(token)` (same scheme as client tokens); the raw value is returned only once at mint, ordinary reads never expose it, connection reveal rotates, and legacy plaintext rows are migrated on open (idempotent). Regression tests: `src/test/agent-token-hash.test.ts`. |
| POD-AUDIT-003 | Medium | fixed | `/pod/watch` authorizes the request, but still trusts the caller-supplied `actor_id` to select the subscription identity. Fixed: watch upgrades now authenticate the caller and bind the subscription to the authenticated principal (owner api token / client token / PIN session / agent bearer); unauthenticated or mismatched bindings are refused (401/403). Regression tests: `src/test/watch-auth.test.ts`. |

## Recommendation

Use a bridge model, not a replacement model:

1. Keep Honcho as the optional primary memory layer for users who want it.
2. Mirror Honcho outputs into Pod as clearly marked third-party/inferred observations.
3. Let Pod remain the durable evidence graph and cross-application substrate.
4. Expose both to Hermes, with Pod as the source of receipts and provenance.

## Evidence highlights

- Pod exposes `/pod/context`, `/pod/observe`, `/pod/session/*`, `/pod/compile`, `/mcp`, and external MCP connector support.
- Hermes already has a dedicated adapter boundary in Pod.
- The live runtime accepted a valid `POST /pod/observe` and returned the observation ID.
- `/pod/query` surfaced raw observations even with `use_llm: false`.

## Follow-up

The next step is to fix the packaging drift and update the docs so the repo matches the current npm-based Smartware release flow.
